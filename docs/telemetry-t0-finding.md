# Telemetry T0 spike: finding (2026-09-10)

The rollout's wave T0 ([rollout-telemetry-and-accounts.md](rollout-telemetry-and-accounts.md))
asked four questions before any product code is written: does the Worker to
Analytics Engine write path work, does the SQL read path work, what is the
free-tier headroom against real payload sizes, and how many web events will
blockers silently drop. All four are answered below with measured numbers. The
Worker is deployed at `db-signals.loominvanta.workers.dev` and receives no
real traffic: no client sends to it, and nothing player-facing changed.

**Verdict: the carrier works and stays. Three things change before T1/T2:**
the data-point budget, not the request budget, is the binding limit and card
rows dominate it (finding 3); the de-duplication salt is per isolate, not
per account (finding 5); and the T3 rollup must use `_sample_interval`
sums, never `count()` (finding 4).

## What was built

- `worker/`: a self-contained Cloudflare Worker (its own `package.json` and
  lockfile, TypeScript, wrangler 4, runtime types generated by `wrangler
  types`; nothing in it touches the game's bundle, lint, or typecheck).
  `POST /v1/signals` validates a body against a strict allowlist for the two
  event types in the spec (exact key set, enums, small-integer buckets, a
  4 KB body cap, at most 60 card rows), computes the daily in-memory hash of
  IP plus coarse browser family, writes to the `db_signals_v1` dataset, and
  returns 204. `GET /health` answers for the kill-switch check. Everything
  else is 404 or 405. CORS allows the Pages origin, localhost dev and the
  Tauri origins only.
- `worker/scripts/send-synthetic.ts`: fires realistic heartbeats and duel
  digests, seven deliberately malformed bodies, and the wrong-method and
  wrong-path probes, reporting bytes, status codes and latency.
- `worker/scripts/query.ts`: the SQL API reader, defaulting to the query
  shape the T3 rollup uses.
- `scripts/measure-save-code.ts`: the save-size measurement, which turned
  out to exist already (section 7); extended with real-catalog profiles
  because wave C0 sizes the Supabase free tier from it.

Deploy path: `npx wrangler deploy` from `worker/`, authenticated by
`CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID` in the owner's user
environment (an account-scoped token: Workers Scripts edit and read, Account
Settings read, Workers Tail read; 1-year expiry). The token is never written
anywhere in the repo or the session record.

## 1. Write path: works, after one cold-start bug

Three synthetic batches (20 heartbeats + 20 duels each, plus a paced batch
of 10 + 10) against the deployed Worker:

| Measure | Heartbeat | Duel |
| --- | --- | --- |
| Body bytes (min / median / max) | 324 / 330 / 336 | 653 / 817 / 1,048 |
| Latency ms from this machine (min / median / max) | 34 / 39 / 127 | 35 / 37 / 49 |
| Status codes, first batch | 19 x 204, **1 x 500** | 20 x 204 |
| Status codes, after the fix | 20 x 204 | 20 x 204 |
| Malformed bodies rejected | 7 of 7 with 400 | |
| `GET /v1/signals`, `GET /nope` | 405, 404 | |

The single 500 was a cold-isolate bug in the hash: the buffer was sized from
the salt before the salt was generated, so the first request on a fresh
isolate threw a RangeError. Fixed and redeployed; the spike exists to find
exactly this class of thing.

Data points written per duel digest: 1 duel row plus one row per card
played, **13 / 18 / 25** (min / median / max) for the synthetic decks, which
play 12 to 24 distinct cards from a 40-card Warchest list.

## 2. Read path: works, and the deploy token could read

`query.ts` against the Analytics Engine SQL API returned the stored rows
grouped by type, with `_sample_interval` sums and distinct-index counts.
Ingestion delay: rows were visible **within 30 seconds** of the write (the
first poll at +30 s already returned them; a 20-second poll in an earlier
attempt returned nothing, so budget 30 to 60 seconds).

**Unexpected: the deploy token was accepted by the SQL API.** The rollout
assumed reading needs a separate token scoped to Account Analytics: Read, and
that is still the right token for T3 (least privilege for a repo secret),
but the split is not enforced by Cloudflare the way the doc implies: a token
holding Workers Scripts read can query Analytics Engine. Consequence: the T3
token should be created and tested on its own, and the deploy token should be
treated as data-reading, which it now is.

## 3. Free-tier headroom: data points bind, and card rows dominate

The spec's headroom estimate counted **requests** (100,000/day, "two digests
per player-day, roughly 50,000 player-days of headroom"). Analytics Engine
also caps **data points written** at 100,000/day, and a duel digest is not one
data point. With the measured shape:

| Per player-day | Requests | Data points |
| --- | --- | --- |
| 1 heartbeat | 1 | 1 |
| 1 duel (median 18 cards) | 1 | 18 |
| 5 duels | 5 | 90 |
| **Player-days per day at the free cap** (5 duels each) | ~16,600 | **~1,100** |

Roughly 1,100 five-duel player-days per day is still far above any near-term
audience, but it is fifteen times tighter than the number in the spec, and the
card rows are 95% of it. Options, for an owner decision before T1 (D-T0.1):

- **(a) Cap card rows per duel** at, say, 8 (the cards that resolved most,
  or a deterministic sample), cutting data points per duel to 9 and headroom
  to about 2,200 player-days. Cheapest.
- **(b) Aggregate card counts client-side per UTC day** and send them once
  with the heartbeat, one row per distinct card played that day. A player
  who plays five duels with one deck sends roughly 20 card rows instead of
  90. Preserves the card-level signal at day granularity and keeps rows free
  of any duel reference, which is stronger for the fingerprint rule than the
  current design.
- **(c) Drop card rows from v1** and add them in T3 once volume is known.

Recommendation: **(b)**. It is the same amount of client code as (a), it
gives the balance question ("which cards see play") a cleaner shape than
per-duel rows, and it makes the k-anonymity floor easier to hit because a
card's daily row count is a count of installs, not of duels.

Request-side headroom is not a concern at any option; the Worker free plan's
100,000 requests/day covers 16,000 five-duel player-days.

## 4. Sampling: index choice matters, and rollups must use `_sample_interval`

Analytics Engine samples writes per index value once a single index receives
a high write rate. The first deploy indexed every point by build SHA, so all
synthetic traffic shared one index: **20 heartbeats were stored as 2**, 20
duels as 2, and 360 card rows as 30, with `sum(_sample_interval)` estimating
27, 15 and 336. The redeploy indexes heartbeat and duel rows by the daily
hash (per install) and card rows by card id (per card). Second run, a 20+20
burst in about two seconds from one machine:

| Type | Sent | Stored | Estimated (`sum(_sample_interval)`) | Distinct index |
| --- | --- | --- | --- | --- |
| card | ~360 | 339 to 504 (sliding window) | equal to stored | 164 to 170 |
| heartbeat | 20 | 9 to 13 | 18 to 28 | 1 to 2 |
| duel | 20 | 8 to 12 | 20 to 32 | 1 to 2 |

Card rows spread over 170 indexes were **not sampled at all**. Heartbeats and
duels from one install were sampled about 2x, because a real install never
sends 20 events in two seconds; a paced run at 400 ms between posts looked
the same, so the sampler keys on short-window rate per index either way.
Under real traffic each install is its own index and sends a handful of
events per day, so per-install rows should be effectively unsampled; this is
the case to re-check at T2 with the first real week of data.

Two rules for T3 follow: **every count in a rollup is
`sum(_sample_interval)`, never `count()`**, and per-card results are read as
estimates, which the privacy page already says about the whole dataset.

## 5. The de-duplication salt is per isolate

The spec's identity model keeps the daily salt in Worker memory, never
persisted. Measured: the same machine, same user agent, same day produced
**two distinct hashes** across a burst, because Cloudflare runs the Worker in
more than one isolate (and more than one colo) and each has its own salt.
Consequence: `count(DISTINCT hash)` overcounts installs by up to the number
of isolates that served them in a day. Two options, owner decision (D-T0.2):

- **(a) Accept it.** Distinct-install counts become an upper bound, and the
  privacy property is strictly stronger (no two requests are even guaranteed
  to hash alike). Trend lines still work; absolute install counts do not.
- **(b) Derive the salt from a Worker secret plus the UTC day**, so every
  isolate computes the same hash for the same day. The secret is a Worker
  environment secret set once by the owner and never rotated automatically;
  the hash still rotates daily and still cannot be reversed. This is closer
  to what Plausible and Fathom actually do, and it changes one sentence in
  the spec ("never persisted" becomes "derived from a persisted secret that
  never leaves the Worker").

Recommendation: **(b)**. Daily active installs is the one number the whole
feature was justified on, and (a) makes it an upper bound of unknown slack.

## 6. Blocker loss: no wholesale block of `workers.dev`, and one path rule

Checked 2026-09-10 against the lists that matter: EasyList, EasyPrivacy,
uBlock Origin's `filters.txt` and `privacy.txt`, StevenBlack's unified
hosts, Peter Lowe's list, and AdGuard's Spyware filter. **None blocks
`workers.dev` as a domain.** Every hit is a specific abusive subdomain (97 in
StevenBlack, 9 each in EasyList and EasyPrivacy) or a per-site rule.
EasyPrivacy does carry two path patterns, `||workers.dev/api/event` and
`||workers.dev/js/script.js` (Plausible's proxy paths), so the endpoint is
`/v1/signals` and the Worker never serves a script. Two hagezi lists
returned empty and are unverified.

What this does not measure: the share of players running a blocker that
blocks by heuristic rather than by list, or DNS filters with private lists.
That number can only come from comparing web and desktop volumes after T2,
and the rollout's rule stands: web and desktop completeness rates are never
divided by one another.

## 7. Save-code sizes (for wave C0), and a stale-doc correction

Both telemetry docs said `scripts/measure-save-code.ts` "is proposed but
does not exist". **It has existed since the 1.5 save-code wave (PR #141)**
with a fixture matrix and a stress case; the docs were wrong, and this spike
nearly overwrote it. It is now extended with two profiles drawn from the real
card catalog and reports with and without replays. Measured 2026-09-10
against `MAX_DECODED_SAVE_BYTES` of 1,048,576 and a replay cap of 10:

| Profile | Raw JSON bytes | Deflated bytes | Code length | Code length with replays | Share of limit |
| --- | --- | --- | --- | --- | --- |
| Fresh save | 1,332 | 647 | 1,359 | 1,369 | 0.1% |
| Fixture: collection, 80 cards | 6,033 | 1,229 | 2,393 | 2,404 | 0.6% |
| Fixture: progress and 3 replays | 2,075 | 842 | 1,704 | 2,031 | 0.2% |
| Stress: 5,000 cards, 48 decks, max replays | 372,744 | 35,097 | 62,603 | 63,152 | 35.5% |
| Catalog: mid-game, 200 distinct x2, 10% variants, 5 decks | 13,081 | 4,319 | 7,885 | 8,216 | 1.2% |
| Catalog: veteran, all 1,235 x4, 25% variants, 20 decks | 74,922 | 17,078 | 30,569 | 31,064 | 7.1% |

All rows round-trip through `decode`. A veteran's save is about 17 KB on
the wire, so Supabase's 500 MB free database holds on the order of 25,000
veteran saves before anything else is stored; the C0 sizing can proceed
from these numbers. The one-line replay fixtures add little; a real
ten-replay reel of 40-card games will weigh more, and C0 should measure it
from a live save rather than this matrix.

## Owner decisions raised by the spike

- **D-T0.1** Card rows: cap per duel (a), aggregate per day on the heartbeat
  (b, recommended), or drop from v1 (c).
- **D-T0.2** De-duplication salt: accept per-isolate hashes (a), or derive
  from a Worker secret plus the day (b, recommended).
- **D-T0.3** Where the Worker source lives: it is in `worker/` in this repo
  for the spike, which is where the risk register wanted the validator kept
  next to the client allowlist. Confirm, or move it out.

## What T1 and T2 inherit

- The Worker as built, with the schema changes D-T0.1 and D-T0.2 imply.
- A Cloudflare dashboard rate-limiting rule on the route (not code; not
  set up in the spike).
- The T3 token, created and tested separately (finding 2).
- The pre-existing disclosures the privacy page must carry are unchanged.
